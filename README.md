# HELIX SignTablet

Планшеты в зале показывают рекламу, а когда приходит клиент, оператор или внешняя
система выводит на **один конкретный планшет** документ с его персональными данными,
клиент читает, отмечает согласия и расписывается на экране. Сервер сохраняет подпись,
собирает PDF и возвращает планшет к рекламе, стирая данные клиента.

Сделано на **ASP.NET Core (.NET 10) + SignalR**. Планшеты работают через киоск-браузер
**FreeKiosk** (Android WebView): открывают один адрес, активируются кодом и дальше
получают команды по защищённому WebSocket.

```
 Планшет (FreeKiosk)                        Оператор (браузер)         Внешняя система
 https://signalr.zrobim.it/                 /admin                     /api/ext/*
          │ WSS (SignalR, токен планшета)        │ HTTPS (пароль)           │ X-Api-Key
          ▼                                      ▼                          ▼
 ┌──────────────────  Nginx Proxy Manager (TLS)  ────────────────────────────┐
 │                    proxy → THIS_HOST:5080                                 │
 └───────────────────────────────┬───────────────────────────────────────────┘
                                 ▼
                  ASP.NET Core (Kestrel, :5080)
      ┌──────────────┬───────────────────────┬──────────────────────────┐
      │  KioskHub    │  REST: admin/kiosk/ext│  Статика: плеер, админка │
      └──────┬───────┴───────────┬───────────┴──────────────────────────┘
             │                   ▼
             │        Файлы и JSON: /var/lib/signaturekiosk
             ▼
      Группы SignalR: "kiosks", "dev:{id}", "grp:{id}", "admins"

      И отдельно, в обратную сторону, по локальной сети:
      сервер → FreeKiosk на планшете (http://IP:8080) для управления
```

Полное описание установки и настройки сервера: [`deploy/README.md`](deploy/README.md).

## Главные правила

Три правила, из которых следует почти вся остальная логика. Если что-то в поведении
системы кажется странным, скорее всего причина в одном из них.

**1. Документ всегда уходит только на один планшет.** Не на группу, не на всех.
Документ несёт персональные данные конкретного человека, и адресатом может быть только
тот планшет, за которым он сидит. Реклама наоборот: её можно слать всем, группе или
одному, и настраивается она отдельно, независимо от документа.

**2. Данные клиента живут на планшете ровно столько, сколько идёт подписание.**
После подписи, после возврата к рекламе, после простоя и после отключения планшета
сессия стирается. Есть и фоновая уборка: сессия, брошенная на планшете, который так и
не вернулся на связь, снимается через два часа, чтобы персональные данные не лежали
на диске в ожидании переподключения.

**3. Планшет получает только то, что положено этому клиенту.** Блок, скрытый условием
на тег, не «прячется» на планшете, а вообще туда не отправляется. Разбор документа
происходит на сервере, до отправки.

## Как планшет опознаётся и привязывается

**Первый шаг, разовый.** В админке на вкладке «Планшеты» создаётся одноразовый код
активации вида `7QF3-K92X`, с ограниченным сроком жизни. Код можно сразу привязать к
рабочему месту и группам. На планшете в FreeKiosk открывается адрес сервиса, клиент
вводит код один раз на экране активации. Можно и короче: открыть
`https://signalr.zrobim.it/?enroll=7QF3-K92X`, тогда код подставится сам.

**Что происходит в этот момент.** Сервер создаёт запись планшета с идентификатором
вида `dev-a1b2c3d4e5` (пять случайных байт) и секретом (24 случайных байта). Секрет
отдаётся планшету **один раз** и на сервере не хранится: в `devices.json` лежит только
его SHA-256. Планшет складывает `deviceId.секрет` в `localStorage` своего WebView.
Код активации при этом гасится и повторно не сработает.

**Все последующие подключения.** Планшет присылает этот токен, сервер считает от
секрета SHA-256 и сравнивает с сохранённым, сравнение идёт с постоянным временем
(`CryptographicOperations.FixedTimeEquals`), чтобы по времени ответа нельзя было
подбирать. Имя, рабочее место и группа берутся **из записи планшета на сервере**, а не
из того, что прислал планшет. Подменить их со стороны планшета нельзя.

**Что будет, если токен украдут.** Нажмите «Заблокировать» в админке: токен
перестанет работать немедленно. Если одним токеном пользуются два экрана сразу,
оператор увидит уведомление «Один код используется на нескольких экранах»: это важно,
потому что документ с персональными данными отрисовался бы на обоих. Планшеты при этом
не отключаются принудительно, иначе перезагрузка страницы на настоящем планшете могла
бы навсегда заглушить его в пользу чужого экрана.

**Проверить, какой планшет физически перед вами:** кнопка «Опознать» на карточке,
планшет крупно покажет номер на экране.

### Может ли идентификатор планшета измениться

Нет. `dev-a1b2c3d4e5` выдаётся один раз при активации и после этого принадлежит **записи
планшета на сервере**, а не самому устройству. Он не меняется ни при перезагрузке
планшета, ни при перезагрузке сервиса, ни при смене Wi-Fi, IP или имени планшета, ни при
переносе планшета на другое рабочее место. Планшет вообще не участвует в выборе
идентификатора: он помнит только выданный ему токен.

Измениться идентификатор может ровно в одном случае: если планшет **потерял токен** и
его активировали заново. Тогда это уже новая запись с новым идентификатором, а старая
остаётся в списке и её нужно удалить. Токен теряется при полной очистке данных
приложения (Android: «Очистить данные», не «Очистить кэш»), при переустановке FreeKiosk,
при сбросе планшета к заводским настройкам и при удалении или блокировке записи в
админке.

Чтобы случайная чистка не стоила переактивации, планшет хранит токен **в двух местах
сразу**: в `localStorage` и в долгоживущей cookie. В Android WebView это чистится разными
вызовами, поэтому частичная чистка привязку не рвёт: уцелевшая копия восстанавливает
вторую при следующем открытии страницы. Полная чистка данных стирает обе, и это ожидаемо.

### Два разных идентификатора, и не надо их путать

На карточке планшета видны оба:

| Что | Пример | Для чего |
|-----|--------|----------|
| Код рабочего места | `WS-204` | им внешняя система адресует планшет: `workstationExternalId` |
| ID планшета | `dev-a1b2c3d4e5` | внутренний: стоит в логах, уведомлениях и записях подписей |

**Обычный способ адресации из внешней системы это код рабочего места.** Его задаёт сам
интегратор на вкладке «Места», он совпадает с тем, как стойка называется в их системе, и
не меняется при замене планшета: сломался планшет, поставили новый, привязали к тому же
рабочему месту, и внешняя система ничего не заметила.

**Страницу планшета можно открыть и в браузере оператора.** Токен планшета проверяется
раньше куки входа в админку, поэтому такое окно работает как настоящий планшет, а не как
админ: у него свои каналы, ему приходит документ и он виден в списке. Прав это никому не
добавляет, потому что токен даёт только личность планшета, а она заведомо меньше прав
администратора. Если токена нет вовсе, планшет показывает экран активации, и в журнал
оператора это не пишется: открыть страницу не значит сломать службу.

ID планшета нужен в трёх случаях: сверить строку лога или запись подписи с конкретным
планшетом, адресовать планшет напрямую параметром `deviceId`, и когда к одному рабочему
месту привязано несколько планшетов. В последнем случае API намеренно отказывается
выбирать сам и просит указать планшет: документ несёт персональные данные, и показать его
не на том экране хуже, чем вернуть ошибку.

Оба значения на карточке копируются нажатием.

## Документ: из чего он состоит

Документ один на всю систему, это шаблон. Персональные данные подставляются в него в
момент отправки на планшет.

**Страницы.** Клиент листает их кнопками «Далее» и «Назад», может вернуться и
перечитать. Последние два экрана всегда одни и те же: подпись и «Спасибо».

**Блоки.** Страница состоит из блоков. Блок это либо текст, либо картинка с заданной
шириной. У каждого блока может быть своё условие показа.

**Страница со скрывающим условием не показывается.** Если условие страницы не выполнено,
клиент её не увидит и при листании она пропускается, не попадая и в счётчик шагов. Это
важно: её отметки в запись не идут, и показывать страницу, галочки с которой никуда не
попадут, значит вводить человека в заблуждение.

**Порядок внутри страницы свободный.** Блоки текста, чекбоксы и двойные зависимые
чекбоксы стоят в одном общем списке, в том порядке, в каком их расставил оператор.
Пункт можно поставить сразу под своим абзацем, а не в общую кучу внизу страницы: в
соглашении галочка почти всегда относится к конкретному абзацу над ней. Этот же порядок
уходит на планшет, в предпросмотр и в запись подписи. Документы, сохранённые до
появления свободного порядка, выглядят как раньше: сначала текст, потом чекбоксы, потом
зависимые чекбоксы.

**Длинное слово без пробелов переносится.** Разделитель из полусотни звёздочек, длинная
ссылка, длинный номер документа: такое слово разрывается по символам и на планшете, и в
предпросмотре, и в PDF. Иначе оно раздвигает страницу, планшет начинает ездить пальцем
вбок, хотя полосы прокрутки не видно, а хвост строки вместе со знаком препинания уходит за
край и в PDF просто пропадает.

**Оформление.** Текст хранится не как HTML, а как набор «фрагментов»: у каждого свои
жирность, курсив, размер и цвет. Поэтому одно и то же оформление гарантированно
одинаково выглядит на планшете и в PDF, и через текст невозможно протащить разметку.

**Три вида страницы.** Кнопка «Добавить страницу» предлагает выбор: обычная страница,
экран подписи и экран сканирования кода. Экран это отдельный шаг, где клиент занят только
одним делом: расписаться или поднести код. На таком экране есть заголовок и текст над полем,
но нет чекбоксов, нет второго поля и туда не дописываются пункты, присланные по API.

То же самое можно поставить и **блоком внутри обычной страницы**, если подпись относится к
конкретному абзацу, а не ко всему шагу. Оба способа дают одно и то же поле: в записи подписи,
в PDF и в раскладке разницы нет. Разница только в том, что видит клиент: отдельный экран или
поле среди текста.

**Поле подписи внутри страницы.** Документ может требовать нескольких подписей: согласие
пациента, отдельное согласие законного представителя, подтверждение отказа. Поле подписи
добавляется на страницу так же, как блок текста или пункт, и стоит там, где его поставил
оператор. У каждого поля своё имя, поэтому в записи подписи и в PDF видно, что именно
подписано, а картинки лежат отдельными файлами (`signature-patient.png`). Обязательное поле
держит кнопку «Далее» и подсвечивается, если человек попробовал пройти дальше не расписавшись.
Итоговая страница подписи в конце остаётся: она даёт главную подпись под всем документом.

**Сканирование кода внутри страницы.** Клиент подносит к камере штрихкод пробирки или QR из
направления прямо по ходу подписания. Считанный код показывается ему крупно, чтобы можно было
сверить, и уезжает в запись подписи вместе со всем остальным. **В PDF код не печатается:** это
служебные данные заказа, а не то, что человек подписывает. В общий список сканирований на
вкладке «Сканировать ШК/QR» такой код тоже не попадает: он принадлежит документу.

**Страница подписи.** Поле подписи стоит по центру экрана: клиент расписывается на весу,
и тянуться к краю планшета неудобно. Блоки размещаются и **над** полем, и **под** ним:
реквизиты, печать, заключительная фраза. Условия показа работают и там.

**Резервная копия.** Кнопки «Экспорт» и «Импорт» на вкладке «Документ» сохраняют все
страницы в файл и восстанавливают обратно. Импорт заменяет страницы целиком, так что
перед крупными правками полезно сделать экспорт.

**Предпросмотр.** Кнопка «Предпросмотр» показывает документ так, как его увидит
клиент, с тестовыми значениями тегов и с применёнными условиями. В окне задаётся всё, что
может прийти по API: значения тегов, состояние именованных чекбоксов документа, выбор в
двойных зависимых чекбоксах и дополнительные чекбоксы, которых в документе нет. Кнопка
«Проверить на планшете» отправляет ровно эти значения на выбранный планшет так, как их
прислала бы внешняя система: удобно посмотреть документ на живом экране. Порядок элементов,
экран подписи и всё остальное совпадают с планшетом один в один. Для тега с
фиксированным набором значений предлагается список, поэтому проверить и мужской, и
женский вариант можно, не выходя из окна: кнопка «Изменить значения» возвращает к вводу.
На планшеты при этом ничего не отправляется.

**Под полем присланных чекбоксов есть готовый пример запроса.** Он свёрнут, разворачивается
по щелчку и обновляется по мере набора: там ровно то тело `POST /api/ext/show-document`,
которое должна прислать внешняя система, вместе с массивами `checkboxes` и `groups`. Массивы
показаны всегда, даже пустыми, иначе их вид нельзя разглядеть до первого набора. Адресуется
рабочее место (`workstationExternalId`), а не внутренний идентификатор планшета: именно так
и надо адресовать снаружи.

**Пол пишется по-русски, а передаётся по-прежнему.** В админке в списках выбора стоят
«М (мужской)» и «Ж (женский)», а на проводе значение остаётся `M` и `F`: так его шлёт внешняя
система и так записаны уже существующие условия. Принимается и то, и другое написание,
включая кириллические `М` и `Ж`: латинская `M` и русская `М` выглядят одинаково, и требовать
одного написания значит собирать ошибки на ровном месте.

**Предпросмотр не только показывает, но и работает.** Пункты в нём отмечаются, в группах
выбирается вариант, а условия пересчитываются на месте. Это не украшение: блок, который
появляется по отметке клиента, иначе нельзя было проверить вообще, он просто никогда не
показывался бы. «Далее» так же не пускает дальше, пока не отмечено обязательное, а
страница со скрывающим условием так же выпадает из потока и из счётчика шагов.

### Как устроен редактор

Вложенность видна по цвету левой полосы: страница зелёная, блок текста синий, чекбокс
янтарный, двойные зависимые чекбоксы фиолетовые.

**Порядок** страниц и элементов внутри страницы меняется мышью за ручку слева.
Перетаскивание начинается только с ручки, поэтому выделять текст внутри блока можно как
обычно. Между элементами всегда видна тонкая полоса «вставить сюда»: по нажатию она
предлагает добавить блок текста, чекбокс или двойные зависимые чекбоксы прямо в это
место. Тащить новый элемент из конца длинной страницы не нужно.

**Добавление страницы** есть и в оглавлении слева, которое закреплено на экране, и
внизу списка страниц. Новая страница сразу показывается на экране.

**Вставка текста из Word, PDF и с сайтов.** Из буфера обмена приходит чужая разметка:
свои шрифты, кегль в пунктах, таблицы, списки, неразрывные пробелы и переносы строк
прямо внутри тегов. Раньше редактор показывал это как есть, а документ такого не хранит,
и на планшете тот же текст выглядел иначе: строки рвались там, где их перенёс Word.
Теперь вставляемое приводится ровно к тому, что документ умеет: жирный, курсив, цвет,
размер и переносы строк. Маркеры и номера списка становятся обычным текстом, строки
таблицы отдельными строками, служебная разметка отбрасывается. Что показал редактор, то
и увидит клиент.

**Кнопка «¶» в панели блока** склеивает перенесённые строки: одиночные переносы посреди
предложения становятся пробелами, а пустая строка между абзацами остаётся границей
абзаца. Нужна после копирования из PDF, где каждая строка приходит отдельной. Операция
явная, потому что в адресе или в реквизитах переносы бывают осмысленными.

**Имя для API** есть у чекбокса, у двойных зависимых чекбоксов и у каждого их варианта.
Оно подставляется само из текста, латиницей: набрали «Гормоны», получили `gormony`. Имя
остаётся на виду, его можно поправить руками, и тогда оно больше не меняется.

Зачем оно нужно: по этому имени внешняя система задаёт начальное состояние пункта или
присылает выбранный вариант, и по нему же на пункт ссылаются условия показа. Без имени
пункт работает и попадает в запись подписи, но задать его из API и сослаться на него в
условии нельзя. Вариант без имени не сохраняется вовсе: адресовать его было бы нечем.

**Панель оформления одна на всю страницу.** Она стоит на своём месте над списком страниц и
прилипает под шапкой при прокрутке, а пока поле не выбрано, просто неактивна. Раньше своя
панель была у каждого блока и каждого заголовка: на документе из пяти страниц это пятнадцать
одинаковых панелей и почти четыреста кнопок на одном экране. Всплывающую над полем панель
пришлось отвергнуть: она закрывала собой то, что было выше, а это кнопка условия показа,
подписи и часть текста.

**Выравнивание стоит в той же панели.** Четыре кнопки: по левому краю, по центру, по правому
и по обоим краям. Кнопка относится к тому полю, в котором стоит курсор, и та, что выбрана
сейчас, подсвечена. Подробнее в разделе «Выравнивание текста».

**Элементы сворачиваются в строку.** Блок текста и двойные зависимые чекбоксы сворачиваются
до одной строки с началом содержимого, как и страницы. Пункт и так занимает одну строку:
условие показа стоит в ней же, а не под ней.

**Несохранённое не теряется.** Пока правки не сохранены, рядом с кнопкой «Сохранить» горит
пометка, черновик каждые пару секунд пишется в браузер, а при попытке закрыть вкладку
браузер переспрашивает. Если работу всё же прервали, при следующем открытии вкладки
«Документ» предлагается восстановить черновик.

**Перетаскивание между страницами.** Пункт или блок переносится на другую страницу тем же
перетаскиванием за ручку. У края окна страница прокручивается сама, поэтому дотянуться можно
до любой страницы, а не только до соседней.

**Сворачивание.** Страница сворачивается в одну строку со сводкой: заголовок, сколько
блоков, чекбоксов и зависимых, есть ли условие. Свёрнутая помечена серой полосой и
приглушённым фоном. В оглавлении есть «Свернуть все» и «Развернуть все».

**Оглавление слева.** Список страниц по заголовкам, клик прокручивает к нужной. Экраны
подписи и «Спасибо» перечислены там же: клиент их видит, а в редакторе про них забывают.

**Один шрифт везде.** Текст блоков, чекбоксы, варианты выбора и текст на странице
подписи выводятся одним размером и с одним межстрочным интервалом. Чужой шрифт или
кегль, попавшие в разметку при вставке, на вид не влияют.

**Условие** показано компактной строкой вида «только если Пол равно F» и разворачивается
по нажатию. Пока условия нет, на его месте ссылка «+ условие показа».

**Проверка.** Кнопка «Проверить», и та же проверка перед отправкой на планшет. Отправку
она не запрещает, а показывает список замечаний: условие на несуществующий тег или имя,
условие без значения, значение, которого нет среди вариантов, повторяющиеся имена,
чекбокс без текста, группа без имени или с одним вариантом, пустой блок, пустая
страница, тег с опечаткой. Всё это иначе выясняется на планшете перед клиентом.

## Теги: подстановка данных клиента

В тексте пишется `{{ФИО}}`, при отправке на планшет на это место подставляется
значение из запроса. Теги работают в заголовках, в тексте блоков, в подписях
чекбоксов и в заголовках групп.

| Тег | Что это | Значения |
|-----|---------|----------|
| `ФИО`, `ДР`, `Адрес регистрации` | данные клиента | любой текст |
| `Пол` | пол | `M` или `F` (принимается и `М`, `Ж`, `муж`, `жен`) |
| `email`, `telephone`, `document`, `date` | контакты, документ, дата | любой текст |
| `cross-border` | трансграничная передача | `true` или `false` |
| `urine` | признак | `true` или `false` |
| `UG` | признак | `true` или `false` |
| `text1` … `text10` | произвольные тексты из внешней системы | любой текст |

**Таблица это не ограничение.** В `fields` можно прислать поле с любым именем, и если такой
тег стоит в тексте или в условии, он заполнится. Таблица это то, что уже согласовано и
предлагается в подсказках редактора. Свой тег в редакторе показывается отдельной строкой
«Свои теги», а не помечается ошибкой.

**Поля, которых в документе нет, просто не используются.** Запрос принимается, ошибки нет.
В подписанный документ, в PDF и в запись подписи попадают только те поля, которые документ
действительно использует: человек видел и подписывал именно их, а хранить лишние
персональные данные незачем. Служебные поля внешней системы (номер заказа, внутренний
идентификатор) можно слать спокойно, они нигде не всплывут.

**Прислать можно любой тег из этой таблицы, не только те, что уже стоят в документе.**
Во вкладке «Документ» под панелью кнопок перечислены все теги, которые принимает API.
Те, что используются в текущем документе, выделены зелёным, поэтому видно и весь список,
и что из него задействовано. По нажатию тег копируется, чтобы вставить его в текст.

### Регистр в именах тегов не важен

Имена сравниваются без учёта регистра **на всём пути**: при подстановке в текст, при
проверке условий показа и при разборе запроса. Внешняя система пишет имя так, как ей
удобно, а документ так, как удобно оператору, и они всё равно встретятся.

```json
{ "фио": "Иванова Анна", "ПОЛ": "F", "адрес регистрации": "Минск", "TELEPHONE": "+375291234567" }
```

Такой запрос заполнит `{{ФИО}}`, `{{ПОЛ}}`, `{{Адрес регистрации}}` и `{{telephone}}` в
тексте и включит блок с условием `Пол` равно `F`. Список незаполненных тегов в ответе
возвращается в том написании, в каком они стоят в документе, чтобы их было легко найти.

Это отдельно закреплено тестом: он шлёт имена в третьем варианте написания и проверяет и
подстановку, и срабатывание условий в обе стороны.

Неизвестный тег остаётся в тексте как есть, `{{вот так}}`. Это сделано намеренно:
пропущенное поле видно сразу, а не превращается в пустое место. Тег, которого нет в
таблице, отмечается красным прямо в списке тегов: почти всегда это опечатка, и увидеть её
надо в редакторе, а не когда клиент прочитает `{{ФИ0}}` на планшете. В ответе на
`show-document` приходит `missingPlaceholders` со списком того, что не передали.

**Булевы теги принимают только `true` или `false`.** Принимается и настоящий
JSON-булев, и строка, регистр не важен:

```json
{"urine": true}       ✔    {"urine": "true"}   ✔    {"urine": "TRUE"}  ✔
{"urine": "да"}       ✘    {"urine": 1}        ✘
```

Настоящий булев принимать обязательно: разработчик интеграции пишет
`new { urine = true }` и получает `true` без кавычек. Неверное значение отклоняется
с кодом 400 и с именем тега в тексте ошибки, а не молча скрывает блок.

Список тегов и допустимые значения отдаёт сам сервер, `GET /api/admin/field-schema`.
Редактор берёт их оттуда, поэтому список в интерфейсе и список в проверке не могут
разойтись.

## Условия показа

Блок, страницу, чекбокс или группу можно показывать по условию. Условие это «поле,
операция, значение», операции: равно, не равно, пусто, не пусто, одно из, возраст меньше,
возраст от.

**Условие по возрасту.** Внешняя система присылает только дату рождения, а документ сам
решает, кому что показать. Операции «возраст меньше, лет» и «возраст от, лет» считают полные
годы из даты на момент показа. Типичный случай: блок для законных представителей показывается
при «возраст по ДР меньше 14 лет», а взрослый вариант при «возраст по ДР от 18 лет». Через
«и» собирается и промежуток: «от 14» и «меньше 18».

Тег выбирать не надо: как только выбрана операция по возрасту, тег с датой рождения
подставляется сам. Другого тега в таком условии быть и не может, потому что возраст считается
только из даты рождения, и список в этот момент подписан «выберите тег с датой рождения».

Дата принимается в привычных видах: `01.01.1990`, `1990-01-01`, `17/05/1990`. Если её не
удалось разобрать, запрос отклоняется с кодом 400 и с именем тега, а не молча скрывает блок.
Если даты нет вовсе, возрастные условия просто не выполняются, и это не ошибка.

**Условие без выбранного тега не сохраняется, и об этом говорят вслух.** Такая строка
обведена красным с подписью «выберите тег, иначе условие не сохранится», «Проверить» называет
число таких строк, а «Сохранить» предупреждает, что они не сохранены и содержимое покажется
всем. Раньше незаполненное условие исчезало молча, и блок молча становился видимым для всех.

**Условие по сроку.** Операция «до годовщины не больше, дней» считает, сколько дней между
сегодняшним днём и годовщиной даты из тега. Считается день и месяц, год не важен: это случай
дня рождения, где сравнивать полную дату бессмысленно, она в прошлом на десятки лет.

**Окно задаётся отдельно до и после.** В строке условия два числа: сколько дней до даты и
сколько после. Одинаковые числа означают одно и то же окно в обе стороны.

| Что нужно | Дней до | Дней после |
|-----------|---------|------------|
| неделю до дня рождения, сам день и неделю после | 7 | 7 |
| две недели до и один день после | 14 | 1 |
| только сам день и месяц после, заранее ничего | 0 | 30 |
| только заранее, в сам день уже нет смысла | 14 | 0 (покажется и в сам день) |

Сам день попадает в оба окна, поэтому нули с обеих сторон означают ровно этот день.

Например, поздравление показывается при «до годовщины по ДР не больше 7 дней»: неделю до дня
рождения, сам день и неделю после. А напоминание о приёме при «до даты по date не больше 3
дней». 29 февраля в невисокосный год считается по 28-му: иначе такое условие не сработало бы
ни разу.

Дата принимается в тех же видах, что и для возраста. Будущая дата это не ошибка: приём и
назначают на завтра. Если даты нет или её не удалось разобрать, условие не выполняется, а о
неразобранной дате приходит ошибка с именем тега.

**Несколько условий через «и».** Кнопка «и ещё условие» добавляет строку: содержимое
показывается, только если выполнены все строки сразу. Например «Пол равно F и UG равно
true». Ограничение: не больше пяти условий в одном наборе.

**Несколько наборов через «или».** Кнопка «или другой набор» начинает новый набор:
содержимое показывается, если выполнен целиком хотя бы один из наборов. Например
«(Пол равно Ж и возраст по ДР меньше 14) или представитель отмечен». Каждая строка после
первой сама говорит, чем она присоединена, и это можно поменять в любой момент.

«И» связывает сильнее «или», как и принято: «А и Б или В» читается как «(А и Б) или В».
Скобки оператор не расставляет, и вложенности нет: любое условие раскладывается в набор
наборов, а дерево со скобками на экране всё равно не показать. Свёрнутая строка условия
пишет то же самое словами и сама ставит скобки там, где наборов больше одного:
«только если (Пол равно Ж и возраст по ДР меньше 14 лет) или представитель равно true».
Ограничение: не больше пяти наборов.

Для «или» по значениям одного тега проще операция «одно из»: она принимает список через
запятую и не требует отдельного набора на каждое значение.

**Отрицание: пометка «не» на строке.** У каждой строки условия есть пометка «не»: часть должна
быть НЕ выполнена. Вместе со связкой «и» это и есть «и не» («Пол равно Ж и не представитель
отмечен»), вместе с «или» это «или не», а на первой строке просто «не». Включённая пометка
заметно окрашена: она переворачивает смысл всей строки.

Пометка сделана отдельной, а не новыми операциями, потому что у сравнений обратное уже есть:
«равно» и «не равно», «пусто» и «не пусто», «возраст меньше» и «возраст от». Без обратного
оставались ровно два случая, и пометка закрывает именно их: «ни одно из перечисленного» и «не
в окне годовщины».

Свёрнутая строка условия пишет обратное словами, а не приставляет «не» перед фразой: «Пол не
равно Ж», «Гражданство ни одно из RU,BY», «возраст по ДР от 14 лет». Так видно итоговый смысл,
а не запись, из которой его надо выводить в уме. Двойное отрицание тоже сворачивается: «не» на
операции «не равно» показывается как «равно».

**Отрицание в точности обратно, включая случай непришедшего тега.** Обычное условие по возрасту
при отсутствующей дате рождения не выполняется, значит отрицание при той же дате выполняется.
Иначе клиент, которого оператор разделил на две ветки, «младше 14» и «не младше 14», не увидел
бы ни одной. О неразобранной дате при этом по-прежнему приходит ошибка с именем тега; молча
пропадает только полностью отсутствующая.

**Наборы решаются по отдельности.** Часть набора может быть про тег (считается на сервере),
часть про чекбокс (считается на планшете). Набор, чья теговая часть не выполнена, отбрасывается
целиком и на планшет не едет. Набор, выполненный по тегам полностью, делает содержимое видимым
сразу, и остальные наборы уже не важны. До планшета доезжают только те наборы, где осталось
что вычислять, и только их чекбоксовые части: про пол клиента планшет по-прежнему ничего не
узнаёт.

Условия сравнивают имена тегов без учёта регистра. Внешняя система может прислать `пол`,
`Пол` или `ПОЛ`, а условие в документе написано как угодно: сработает в любом случае.
Так же работает и подстановка `{{ПОЛ}}`.

Важно понимать, что условия бывают **двух разных природ**, и ведут они себя по-разному.

### Условие на тег: считается на сервере

Пример: показать блок, если `Пол` равно `F`. Сервер вычисляет это **до** отправки на
планшет, и блок, который клиенту не положен, на планшет вообще не уезжает. Это часть
третьего главного правила: чужой текст физически не оказывается на устройстве.

### Условие на чекбокс или группу: считается на планшете

Пример: показать блок, если клиент отметил `marketing`. Такое условие нельзя решить
заранее, потому что оно зависит от того, что человек сделает через секунду. Блок
уезжает на планшет вместе со своим условием и появляется или исчезает прямо в момент
нажатия, без обращения к серверу. Утечки это не создаёт: содержимое блока это шаблон,
одинаковый для всех, а персональные данные подставлены в него уже для этого клиента.

В редакторе оба вида лежат в одном выпадающем списке, но разными разделами: «Теги из
API», «Чекбоксы в документе», «Двойные зависимые чекбоксы».

### Смешанное условие: часть на сервере, часть на планшете

В одной связке через «и» могут стоять условия обеих природ: «Пол равно F и согласие
отмечено». Сервер считает свою часть до отправки. Если она не выполнена, содержимое на
планшет не уезжает вообще. Если выполнена, на планшет отправляется только оставшаяся
часть, про чекбокс. Значение тега планшету при этом не сообщается: ему незачем знать
данные, которые он не показывает.

### Три правила, которые здесь легко упустить

**Скрытый обязательный пункт не блокирует «Далее».** Иначе клиент упирается в галочку,
которой не видит, и выйти из документа не может.

**Чекбокс внутри скрытого блока считается неотмеченным.** Благодаря этому взаимные
ссылки (блок A зависит от галочки в блоке B, а B от галочки в A) разрешаются сами и
не зацикливаются.

**Страница перерисовывается, только если от нажатого пункта что-то зависит.** Иначе
она дёргалась бы под пальцем на каждой галочке.

## Чекбоксы и двойные зависимые чекбоксы

### Обычный чекбокс

Пункт согласия. Может быть обязательным, тогда без него не работает «Далее».

**Текст пункта оформляется как обычный абзац.** Панель над редактором работает и здесь:
жирный, курсив, цвет, размер. Слово, выделенное в пункте, так же выделено на планшете, в
предпросмотре, в окне наблюдения и в PDF. Простой текст пункта при этом всегда держится в
согласии с оформленным: по нему пункт узнают в записи подписи, в API и в списке недостающего,
и оформление там ни к чему.

### Именованный чекбокс

Если задать чекбоксу **имя для API**, внешняя система сможет задать состояние именно
ему:

```json
"checkboxes": [{"key": "consent", "checked": true}]
```

Текст берётся из шаблона, но его можно переопределить полем `label`.

Чекбокс **без** имени и чекбокс с **незнакомым** именем ведут себя по-старому: просто
дописываются на страницу, у которой отмечена галочка «Показывать здесь чекбоксы,
присланные по API».

### Двойные зависимые чекбоксы

Набор, где выбрать можно **только один** вариант, и «ни одного» это тоже допустимое
состояние. Например «Трансграничная передача: разрешаю / запрещаю / не выбрано».

```json
"groups": [{"key": "transfer", "selected": "deny"}]
```

Пустое `selected` снимает выбор. Группа может быть обязательной, тогда без выбора не
работает «Далее».

**Варианты стоят в одну строку.** Вопрос сверху, ответы под ним в ряд: их два или три и они
короткие, а в столбик ответ отрывался от вопроса и занимал пол-экрана впустую. Длинные
варианты и длинный список переносятся на следующую строку сами.

**Текст оформляется как обычный абзац.** Заголовок группы и текст каждого варианта правятся
той же панелью, что и абзацы: жирный, курсив, цвет, размер. То же самое у обычных пунктов.

**Вариант можно отметить заранее.** В редакторе у каждого варианта есть галочка «отмечен»;
отмеченным может быть только один. Раньше выбор по умолчанию задавался только по API и
стирался при первом же сохранении из конструктора.

Нарисована группа **чекбоксами, а не радиокнопками**, и это осознанно: нажатие по уже
выбранному варианту снимает его и возвращает группу в третье состояние. Радиокнопки
так не умеют, снять выбор в них нельзя.

### Имена чекбоксов и теги живут раздельно

Тег `urine` и чекбокс с именем `urine` это **разные вещи**. Тег подставляется в текст
и участвует в условиях, чекбокс это элемент, который клиент нажимает. Присланное поле
`urine = true` не отмечает чекбокс с таким же именем. Сделано намеренно: одно имя не
должно значить две вещи, иначе однажды это выстрелит.

---

### Если клиент не отметил обязательный пункт

Кнопка «Далее» остаётся рабочей. По нажатию система показывает, чего именно не хватает:
пропущенные пункты обводятся красным, под каждым появляется подпись словами («Нужно
отметить, чтобы продолжить», у групп «Нужно выбрать один вариант»), экран подводится к
первому из них, а внизу написано, сколько осталось.

Так сделано намеренно. Выключенная кнопка на нажатие не отвечает ничем: человек видит серый
прямоугольник, не понимает, чего от него хотят, и ищет неотмеченную галочку среди десятка
глазами. Подсветка появляется только после попытки перейти дальше, а не заранее: винить
человека до того, как он что-то сделал, незачем. Как только пункт отмечен, подсветка с него
снимается сразу, и счётчик уменьшается.

Цветом дело не ограничивается: есть значок и текст, потому что цвет не различит человек с
нарушением цветовосприятия и не заметит тот, кто смотрит на планшет под углом. Короткое
покачивание привлекает взгляд один раз и отключается, если в системе выключены анимации.

То же на экране подписи: кнопка «Подписать» рабочая, и по нажатию подсвечивается пустое поле.

## Что происходит при подписании

1. Клиент листает страницы, отмечает согласия, расписывается пальцем или стилусом.
2. Планшет отправляет `POST /api/sign`: отметки (с ключами), выбор в группах, картинку
   подписи в PNG и `submissionId` этой сессии.
3. Сервер **пересчитывает условия заново** по финальным отметкам клиента. В запись и в
   PDF попадает ровно то, что человек видел перед собой. Скрытый пункт не записывается
   как сознательный отказ.
4. Запись сохраняется, сессия планшета стирается, генерируется PDF.
5. Админка получает уведомление и показывает новую подпись без перезагрузки.

**Повторная отправка безопасна.** Если ответ потерялся и планшет отправил подпись
ещё раз, `submissionId` не даст создать второй пустой дубль: сервер вернёт ту же
запись.

**Что лежит в записи:** заголовок документа, время, планшет и рабочее место, значения
тегов, все пункты с ключами и отметками, группы отдельным списком вместе со всеми
вариантами, из которых выбирали, и сам разобранный документ.

**Отрисовка подписи.** Линия идёт за наконечником без задержки: у библиотеки отключены
два ограничителя, которые по умолчанию выбрасывали точки ближе пяти пикселей к предыдущей и
обрабатывали движение не чаще раза в 16 миллисекунд. Плюс читаются промежуточные точки
пера, которые планшет успевает снять между кадрами, иначе быстрый росчерк рисовался
несколькими прямыми срезами.

**PDF** собирается на сервере через PDFsharp со встроенным шрифтом DejaVu, поэтому
кириллица не зависит от шрифтов системы. Отметки печатаются там же, где их видел клиент:
пункт стоит под своим абзацем, а не в общем списке в конце. Иначе по документу нельзя
понять, к чему относится согласие. Группа печатается заголовком и всем набором вариантов
с отметкой у выбранного, а если не выбрано ничего, так и написано. Если в записи есть
пункт, которому не нашлось места в документе, он всё равно печатается отдельным списком:
из записи подписи ничего не теряется. Если PDF почему-то не собрался при подписании,
он будет собран заново при первом скачивании.

**Место под подпись всегда одного размера**, независимо от того, насколько размашисто
расписался человек. Иначе длина документа зависела бы от почерка, и раскладка подписей
(ниже) не совпадала бы с готовым файлом. Обычный размер это 280 × 100 точек, и его можно
уменьшить настройкой «Подпись в PDF» на вкладке PDF, вплоть до 40 процентов: подпись
занимает на бумаге много места даже тогда, когда текст уже мелкий.

**Размер шрифта в PDF задаётся отдельно от планшета.** Экран и бумага это разные носители:
на планшете крупный шрифт нужен, чтобы читалось с расстояния, а на бумаге тот же размер
раздувает документ на лишние страницы. Настройка «Шрифт в PDF» на вкладке PDF уменьшает
шрифт только в файле, от 100 до 50 процентов; на планшете размер остаётся тем, что задан в
конструкторе. Поля листа и место под подпись при этом не меняются: они заданы форматом
бумаги, а не размером букв.

## Экран «Спасибо»

Последнее, что видит клиент. Настраивается как обычная страница: заголовок оформляется той же
панелью (жирный, курсив, цвет, размер, выравнивание), под ним можно поставить сколько угодно
блоков текста и картинок. Раньше это была одна строка без оформления.

**Время показа задаётся здесь же**, от двух до шестидесяти секунд. Меньше двух человек не
успевает прочитать, больше минуты планшет впустую занят и следующий клиент стоит перед экраном,
который выглядит выключенным. По истечении времени планшет сам возвращается к рекламе; если
сервер в этот момент недоступен, планшет всё равно уходит с этого экрана и показывает свою
рекламу локально, а не остаётся в тупике.

Личные данные подписанта на этом экране не показываются: заголовок документа стирается сразу
после подписания вместе со всем, что держалось в памяти планшета. На экране остаётся только то,
что собрал оператор.

## Выравнивание текста

Панель оформления над редактором даёт четыре выравнивания: по левому краю, по центру, по
правому краю и по обоим краям. Это свойство всего абзаца, а не выделенного куска: выровнять
половину строки нельзя, поэтому кнопка относится к тому полю, в котором стоит курсор.

Выравнивание одинаково доходит и до планшета, и до PDF. По обоим краям строка растягивается
пробелами между словами, кроме последней строки абзаца: иначе одно слово в конце растянулось
бы во всю ширину листа. Куски слишком длинного слова, разорванного переносом, при этом не
разъезжаются: между ними пробела нет, и растягивать там нечего.

## Картинка и текст рядом

У блока с картинкой есть **обтекание**: картинка встаёт слева или справа, а текст следующих
абзацев идёт рядом с ней и продолжается под ней. Отступ от картинки до текста задаётся отдельно,
до шестидесяти точек: вплотную текст читается плохо.

Работает одинаково на планшете, в предпросмотре и в PDF. В PDF это настоящее обтекание, а не
подгонка на глаз: собственный перенос строк обходит картинку так же, как это делает браузер, а
ниже неё строки снова идут во всю ширину.

- **Обтекать может только текст.** Пункты, двойные зависимые чекбоксы, места подписи и
  сканирования рядом с картинкой не встают: они и так узкие, а рядом с ней превратились бы в
  обрывки. Такой элемент опускается под картинку целиком.
- **Две картинки подряд не встают рядом**: получилась бы колонка из картинок с обрывками текста.
- **Картинка во всю ширину обтекать не может**: текста рядом с ней не поместится, поэтому её
  ширина сама ужимается до семидесяти процентов.
- Новая страница обнуляет обтекание: картинка осталась на прошлой, и держать её отступ дальше
  значило бы сузить текст без всякой причины.

## Размер и положение места подписи

У каждого поля подписи свои **ширина** и **высота** в точках и **положение** (слева, по центру,
справа). Обычные значения это 280 × 100 точек, размер, с которого всё начиналось: документы,
собранные раньше, выглядят как выглядели, точка в точку.

Единицы те же, что и в PDF, поэтому на бумаге получается ровно то, что задано. На планшете поле
занимает ту же долю ширины, что и на листе: 280 точек из 495 это те же 57 процентов и там, и там.
Уже шестидесяти точек расписаться негде, шире 495 место на листе не поместится, выше трёхсот точек
оно занимает лист целиком, поэтому всё это ограничено.

**На экране подписи размер не применяется:** там поле занимает весь экран, в этом и смысл
отдельного экрана. Размер задаётся для поля, стоящего блоком внутри страницы.

Настройка «Подпись в PDF» на вкладке PDF по-прежнему действует поверх этого и уменьшает все места
разом, не трогая заданных пропорций.

## Раскладка подписей на листе PDF

Кнопка **PDF** на вкладке «Документ» открывает листы будущего файла в натуральную
величину. По умолчанию каждая подпись печатается в потоке текста, там же, где стоит её
поле в документе; такое место показано серой рамкой с подписью «в потоке». Если PDF должен
точно повторять готовый бланк, подпись можно снять с потока и поставить в нужную точку
листа мышью: «Разместить», затем перетащить синий прямоугольник и при необходимости
растянуть его за угол.

**Макет не похож на PDF, а совпадает с ним.** Координаты каждой строки считает тот самый
генератор, который потом соберёт файл: сервер прогоняет вёрстку и возвращает готовый
список элементов с их положением на листе. Браузер только рисует присланное, поэтому
шрифты, переносы и разбивка на страницы здесь ровно те же, что в скачанном PDF.

Что стоит знать:

- **Координаты хранятся в долях листа**, а не в точках. Они не зависят от того, в каком
  масштабе оператор смотрел макет, и переживут смену формата страницы.
- **Раскладка пересчитывается на каждое изменение.** Снятая с потока подпись укорачивает
  документ, возвращённая удлиняет, и разбивка на страницы вместе с ней меняется.
- **Одна подпись это одно место.** Двух прямоугольников для одного поля быть не может:
  иначе непонятно, какая из напечатанных подписей настоящая.
- **Значения тегов берутся те же, что в предпросмотре.** Длина подставленного текста
  влияет на то, где закончится страница, а значит и на то, куда попадёт подпись.
- **Если документ стал короче**, чем когда подписи расставляли, они переезжают на
  последний лист, и админка об этом предупреждает. Подпись не теряется никогда.
- **Раскладка ездит вместе с документом**: она попадает в экспорт шаблона и
  восстанавливается при импорте. Поле подписи удалили из документа, его раскладка
  удаляется вместе с ним.
- Что именно уносит экспорт, перечислено в разделе «Экспорт и импорт шаблона».
- На планшете это не видно никак: раскладка касается только печати.
- **Размер шрифта и размер места под подпись** задаются здесь же и пересчитывают макет сразу,
  поэтому видно, во сколько листов уложится документ.

## Сроки показа картинок в рекламе

У каждой картинки на вкладке «Слайды» есть два поля: **с** какого дня показывать и **по** какой,
включительно. Пустое поле означает «без ограничения» с этой стороны, поэтому картинка без обеих
дат показывается всегда, как и раньше.

Считает сроки сервер и по дню, а не по часам: реклама живёт днями, и час начала показа никому не
нужен. Планшет получает уже готовый список и про даты ничего не знает.

- **Картинка сама появляется и пропадает.** При смене суток список пересобирается и уходит на
  планшеты заново: акция, начинающаяся завтра, включится сама, а вчерашняя исчезнет.
- **Правка срока действует сразу**, без перезагрузки планшета.
- **Планшет, на котором идёт подписание, не трогается**: реклама никогда не перебивает документ.
- **Срок наоборот отклоняется**: дата окончания раньше начала означала бы картинку, которая не
  покажется никогда, и молчать об этом нельзя.
- В админке под каждой картинкой написано, показывается ли она сегодня, а картинка вне срока
  показана блёклой: список плейлиста при этом не меняется, она просто ждёт своего дня.

## Наблюдение за экраном планшета

Кнопка **«Смотреть»** на карточке планшета открывает окно, где видно то же, что видит клиент:
те же страницы, те же пункты, подпись появляется штрих за штрихом. Задержка на локальной сети
около десятой доли секунды.

**Картинка не передаётся.** У админки есть тот же отрисовщик документа, что и у планшета,
поэтому планшет присылает не изображение, а короткие сообщения о том, что изменилось: экран,
номер страницы, отмеченные пункты, выбранные варианты, готовые подписи, считанный код. Расход
измеряется сотнями байт на событие вместо мегабит видео, и на планшете не тратятся ни батарея,
ни камера.

**Только просмотр.** В окне нет ни одного поля ввода и ни одной кнопки, кроме «Закрыть».
Отметить пункт за клиента, нажать «Далее» или расписаться отсюда нельзя. Связь односторонняя:
от планшета к наблюдателю, обратно не уходит ничего.

**Камера у оператора не открывается никогда.** Когда клиент сканирует код, окно пишет «открыта
камера» и потом показывает считанный код. Обращения к камере в этом окне нет вовсе, поэтому и
запроса на доступ у оператора не появляется.

**Ничего не сохраняется.** Поток живёт, только пока окно открыто. Ни на сервере, ни в журнале
не остаётся ни записи о наблюдении, ни копии того, что видел оператор. Клиенту на планшете
тоже ничего не показывается.

**Планшет молчит, пока за ним не смотрят.** Сервер включает рассказ, когда появился первый
наблюдатель, и выключает, когда ушёл последний. Смотреть можно только за одним планшетом
одновременно: иначе в одном окне оказались бы данные двух разных клиентов.

**Документ пришёл по API.** Когда документ отправляет внешняя система, а не оператор, в админке
появляется предложение «Документ отправлен на планшет ... Смотреть». Оно ждёт двадцать секунд и
ничего не открывает само: оператор мог быть занят другим, и подменять ему экран без спроса
нельзя.

**Прямая ссылка.** `https://ваш-адрес/admin/#watch=WS-204` открывает наблюдение сразу за
планшетом на этом рабочем месте. Внешняя система может дать такую ссылку оператору рядом со
своим заказом. Адресуется код рабочего места, как и везде в API; имя планшета и внутренний
идентификатор тоже принимаются. Если планшет не на связи, окно не открывается и об этом
говорится прямо.

**Если связь оборвётся,** окно переподключится и перечитает состояние заново: SignalR при
переподключении теряет подписки, поэтому наблюдение восстанавливается целиком, а не
дорисовывается поверх устаревшего.

## Сканирование штрихкодов и QR

Вкладка «Сканировать ШК/QR»: выбираете планшет, нажимаете «Начать сканирование», на
планшете открывается камера с окном наведения.

**Какие коды читаются:**

| Код | Что это |
|-----|---------|
| QR | двумерный, самый привычный |
| Data Matrix | двумерный, мельче QR при том же объёме: им метят пробирки и реагенты |
| EAN-13, EAN-8 | товарные линейные коды |
| Code-128 | линейный, любые символы |
| ITF (Interleaved 2 of 5) | линейный, только цифры и только чётное их количество: транспортная упаковка и пробирки |
После успешного считывания планшет показывает «Код считан», код сохраняется в списке,
и планшет возвращается к обычному экрану.

Работает только фронтальная камера: планшет висит лицом к клиенту, код показывают в неё, а
выбор камеры на экране только сбивал. Нажав «другая камера», человек видел пустой кадр с
обратной стороны планшета и решал, что сканирование сломалось.

**Синхронный запрос из внешней системы.** `POST /api/ext/scan-request` открывает
камеру и **ждёт** результат, возвращая код прямо в ответе. Таймаут задаётся
`timeoutSec` (по умолчанию 60, максимум 300), по истечении приходит 408. Это удобно,
когда внешней системе нужно «попросить клиента показать код» внутри своего сценария.

Библиотека распознавания (`@zxing/browser`) лежит локально: политика безопасности
содержимого запрещает загрузку скриптов со сторонних адресов.

## Управление планшетами по локальной сети

Обычный обмен идёт от планшета к серверу. Здесь наоборот: сервер обращается к
приложению FreeKiosk на самом планшете, поэтому **сервер и планшеты должны быть в
одной локальной сети**. Через интернет это не работает и не должно.

Включается на вкладке «Планшеты», блок «Управление планшетами по локальной сети».
Пока выключено, к планшетам не уходит ни одного запроса.

**Что доступно оператору** с карточки планшета, кнопка «Управление»: обновить
страницу, очистить кэш, перезапустить приложение, перезагрузить планшет, включить и
выключить экран, яркость, звуковой сигнал, произнести текст, показать сообщение,
снимок экрана.

**Здоровье парка.** Раз в 5 минут сервис опрашивает планшеты: заряд, свободное место,
Wi-Fi, версия FreeKiosk и Android, режим Device Owner. Всё видно на карточке. Низкий
заряд и нехватка места поднимают уведомление оператору.

**Автолечение.** Срабатывает, когда планшет отвечает по своему адресу, но не выходит
на связь с сервисом: это признак зависшего браузера. Сначала перезапускается
приложение, потом планшет перезагружается целиком. После трёх безуспешных попыток
автолечение останавливается и оператор получает уведомление, что планшету нужен
осмотр. Первые две минуты после перезапуска сервиса автолечение не работает вообще:
планшеты ещё не успели переподключиться, и без этой паузы обычное обновление сервиса
перезагружало бы весь парк.

**Device Owner** на планшете нужен для перезагрузки и настоящего выключения экрана, а
также блокирует кнопки «Домой» и «Недавние» и шторку уведомлений. Назначается один
раз, подробности в [`deploy/README.md`](deploy/README.md).

**Что сделано, чтобы это не стало дырой.** Адресом управления принимается только
IP-адрес: имена хостов, адреса с путём и петля отклоняются. Команды заданы явным
списком, путь из запроса к планшету не уходит никогда. Редиректы не выполняются, иначе
один неисправный планшет мог бы увести ключ всего парка на посторонний хост. Снимок
экрана ограничен 8 МБ и отдаётся только как изображение. Ключ API хранится только на
сервере и обратно в браузер не возвращается.

## Расписание

Команды по времени для всего парка, группы или одного планшета. Настраивается внизу
вкладки «Планшеты». Типичный набор:

| Время | Дни | Действие | Кому |
|-------|-----|----------|------|
| 06:50 | Пн Вт Ср Чт Пт | Включить экран | Все планшеты |
| 21:00 | каждый день | Выключить экран | Все планшеты |
| 03:30 | Вс | Перезагрузить планшет | Все планшеты |

**Время указывается по часам сервера**, они показаны прямо в заголовке раздела. При
переходе на летнее время правило остаётся в 6:50 по стенным часам, а не уезжает на час.

**Доступные действия:** включить и выключить экран, разбудить, яркость, громкость, вернуть
рекламу, обновить страницу, перезапустить приложение, очистить кэш, перезагрузить планшет,
звуковой сигнал, показать сообщение, произнести текст.

**Дни недели.** Ни одного выбранного дня означает каждый день. Правило срабатывает не чаще
одного раза в сутки, даже если сервис перезапускали.

**Кому:** все планшеты, группа, один планшет или произвольный набор. Набор задаётся прямо в
правиле отметками, без заведения группы: часто нужно «эти три планшета в зале», а
группировать их больше незачем. Есть кнопка «Отметить все». Удалённый планшет из набора
просто выпадает, остальные продолжают работать.

**Планшет, на котором идёт подписание, не трогают.** Галочка «не трогать планшет, где идёт
подписание» включена по умолчанию, и снимать её почти никогда не нужно: погасить экран или
перезагрузить планшет под рукой у подписывающего человека значит потерять его подпись и
заставить начинать заново. В итоге запуска видно, сколько планшетов пропущено по этой причине.

**Если сервис был выключен в назначенный момент.** Безопасные команды (экран, яркость,
громкость, возврат рекламы) выполняются с опозданием до 30 минут: иначе утром можно прийти
к тёмным планшетам. Перезагрузка, перезапуск приложения, очистка кэша и обновление страницы
не догоняются никогда, чтобы опоздавшая команда не перезагрузила парк среди рабочего дня.

**Что нужно, чтобы это работало.** Почти все команды идут по локальной сети через FreeKiosk,
поэтому управление по локальной сети должно быть включено, а сервер и планшеты должны быть
в одной сети. Если управление выключено, раздел прямо об этом предупреждает. Единственное
исключение это «Вернуть рекламу»: она идёт через уже открытое соединение и локальной сети
не требует. Перезагрузка планшета дополнительно требует режима Device Owner.

**Проверить, не дожидаясь времени:** кнопка «Запустить» у правила выполняет его прямо
сейчас и показывает результат. Итог каждого запуска, ручного и по времени, попадает во
вкладку «Логи» и в саму строку правила.

---

### Где можно выбрать несколько планшетов

| Где | Выбор | Почему так |
|-----|-------|-----------|
| Слайды (реклама) | все, группа, один, произвольный набор | реклама не несёт персональных данных, её можно слать куда угодно |
| Расписание | все, группа, один, произвольный набор | командам управления всё равно, сколько планшетов |
| Документ | **только один планшет** | документ несёт данные конкретного человека, и адресатом может быть только тот экран, за которым он сидит |
| Сканирование | **только один планшет** | код читает камера одного планшета, и результат принадлежит именно этому запросу |

Ограничения документа и сканирования не технические, а смысловые, и снимать их не следует.

## Уведомления и логи

**Вкладка «Уведомления».** Планшет пропал со связи дольше заданного времени, посыпались
ошибки, один код на нескольких экранах, низкий заряд, мало места, зависший планшет.
Уведомление гаснет само, как только причина устранена. Можно включить системные
уведомления браузера и звуковой сигнал.

**Вкладка «Логи».** Сбои сервиса и планшетов: ошибки отправки подписи, отказ камеры,
сбои генерации PDF, перезапуски сервиса. Записи переживают перезапуск. Планшеты шлют
свои ошибки сами, с защитой от лавины: одно и то же сообщение не чаще раза в 30 секунд
и не больше десяти за пять минут.

Сюда попадает только то, с чем оператор может что-то сделать. Служебные предупреждения
самой платформы .NET отфильтрованы: они выглядят как поломка, ничего не требуют и прячут
под собой настоящие сбои. Полный вывод, включая их, по-прежнему есть в системном журнале:
`journalctl -u signaturekiosk -n 200`.

**Повреждённый файл данных.** Если файл в каталоге данных окажется испорчен, сервис не
затирает его пустым значением. Файл откладывается рядом под именем с меткой времени
(`devices.json.corrupt-20260820-193000`), в лог попадает запись уровня «ошибка», а
оператор получает уведомление. Записи из отложенного файла можно разобрать руками, и
ничего не теряется безвозвратно.

**Версия страницы на планшете.** Планшет сообщает, какую версию страницы он открыл.
Если WebView не перезагружался с прошлого обновления, карточка планшета показывает
предупреждение. Это не мелочь: старая страница продолжает показывать рекламу и молча
игнорирует всё, что появилось позже, и без этой подсказки понять причину невозможно.

## Экспорт и импорт шаблона

Кнопка «Экспорт» на вкладке «Документ» сохраняет весь шаблон в один файл, «Импорт»
разворачивает его обратно. Файл самодостаточен: его можно перенести на другой сервер.

**Что уносит экспорт:**

| Что | Подробнее |
|-----|-----------|
| Страницы и их вид | обычная, экран подписи, экран сканирования |
| Заголовки и текст | оформление каждого куска: жирный, курсив, цвет, размер |
| Выравнивание | заголовков, абзацев и картинок |
| Картинки | не только ссылка, но и сам файл, целиком |
| Обтекание картинки | сторона и отступ до текста |
| Места подписи | ширина, высота и положение каждого |
| Экран «Спасибо» | заголовок, блоки и время показа |
| Чекбоксы | текст, имя для API, обязательность и отметка по умолчанию |
| Двойные зависимые чекбоксы | заголовок, варианты и вариант, отмеченный заранее |
| Поля подписи и сканирования | и как экраны, и как блоки внутри страницы |
| Условия показа | страниц, блоков, пунктов, групп и полей, включая составные через «и» |
| Настройки PDF | размер шрифта, размер места под подпись, раскладка подписей с координатами |
| Тексты экранов | приглашение к подписи, экран благодарности, возврат к рекламе |
| Пометка приёмника | на какую страницу дописывать чекбоксы, присланные по API |

**Чего в файле нет намеренно:** планшеты, группы, рабочие места, ключи API, расписание,
настройки управления по сети, слайды рекламы и записи подписей. Это шаблон документа, а не
резервная копия системы. Реклама и планшеты привязаны к конкретной установке, и переносить
их вместе с документом значило бы затирать чужую настройку.

**Картинки лежат внутри файла.** Раньше туда попадала только ссылка `/media/имя`, и на другом
сервере вместо печати оставалась пустая рамка. Теперь при экспорте каждая картинка, на которую
ссылается документ, читается из медиатеки и кладётся в файл, а при импорте возвращается под тем
же именем и появляется в медиатеке. Картинка с таким именем, которая уже есть, не трогается:
её могли заменить нарочно. Файлы, выгруженные старой версией, по-прежнему читаются, просто
картинок в них нет.

**Проверено сравнением целиком.** Документ до экспорта и после импорта сверяется поле за полем,
включая вложенность и порядок; расхождений быть не должно ни одного.

## Тексты чекбоксов и групп из API

Формулировка пункта может зависеть от заказа, а место в документе всегда одно и то же.
Поэтому текст можно прислать вместе с данными подписанта, не трогая шаблон.

| Что | Поле | Что делает |
|-----|------|------------|
| Чекбокс | `label` | заменяет текст пункта целиком |
| Чекбокс | `labelAppend` | дописывает к тексту, который стоит в документе |
| Группа | `title` | заменяет заголовок двойных зависимых чекбоксов |
| Группа | `titleAppend` | дописывает к заголовку |
| Вариант | `options[].label` | заменяет подпись варианта |
| Вариант | `options[].labelAppend` | дописывает к подписи варианта |
| Список вариантов | `options` целиком | заменяет набор ответов, который стоит в документе |

```json
"checkboxes":[{"key":"golod","labelAppend":"(с 22:00)"}],
"groups":[{"key":"pisha","selected":"da","title":"Голодание перед сдачей",
           "options":[{"key":"net","labelAppend":", не соблюдал"}]}]
```

Дописка присоединяется через пробел, но если она начинается со знака препинания
(`, . ; : ! ? )`), пробел не ставится: получается «НЕТ, не соблюдал», а не «НЕТ , не соблюдал».

**Варианты ответов можно прислать целиком.** Если в `options` пришёл непустой список, он и
становится набором ответов вместо того, что стоит в документе. Складывать два набора нельзя:
клиент увидел бы на экране и свои варианты, и чужие сразу. Заказ, приходящий со своим списком
ответов, задаётся так:

```json
"groups":[{"key":"pisha","selected":"menee",
           "title":"Сколько прошло с последнего приёма пищи",
           "options":[{"key":"menee","label":"Менее 8 часов"},
                      {"key":"bolee","label":"Более 8 часов"},
                      {"key":"nepomnyu","label":"Не помню"}]}]
```

**Присланный текст живёт до конца этого показа.** Он хранится вместе с остальными данными
подписанта, поэтому переживает переподключение планшета и попадает в запись подписи и в PDF,
но в сам шаблон не записывается: иначе документ дописывал бы сам к себе при каждом показе.

## Внешнее API

### Как это выглядит целиком

Внешняя система шлёт один запрос, и документ появляется на планшете сам, без участия
оператора:

```bash
curl -X POST -H "X-Api-Key: КЛЮЧ" -H "Content-Type: application/json" \
  -d '{"workstationExternalId":"WS-204",
       "fields":{"ФИО":"Иванова Анна","ДР":"01.01.1990","ПОЛ":"F","UG":"true"}}' \
  https://signalr.zrobim.it/api/ext/show-document
```

Что происходит дальше, по шагам:

1. Сервер находит планшет по коду рабочего места (или по `deviceId`, если он передан).
2. Проверяет булевы теги: неверное значение отклоняется с кодом 400 и с именем тега.
3. Подставляет значения в `{{теги}}` по всему документу.
4. Вычисляет условия показа. Блок, который этому клиенту не положен, **на планшет не
   уходит вообще**, а не прячется там.
5. Добавляет присланные чекбоксы и выбор в двойных зависимых чекбоксах.
6. Отправляет готовый документ на **один** планшет и сохраняет его как состояние планшета.

Клиент видит документ через доли секунды. Оператору ничего нажимать не нужно.

**Если планшет в этот момент не на связи**, документ не теряется: он появится на экране,
как только планшет подключится. В админке это видно заранее: в списке планшет помечен
«(офлайн)», окно ввода значений предупреждает об этом, и сообщение после отправки говорит
«планшет не на связи, документ появится при подключении», а не «документ показан». Это отличается от сканирования, которое живёт только в
момент отправки и до выключенного планшета не дойдёт (там сразу возвращается 409).

**В ответе** приходит `missingPlaceholders` со списком тегов, которые не передали. Они
останутся в тексте как `{{вот так}}`, чтобы пропуск было видно.

**Сессия живёт** до подписи, до возврата к рекламе, до срабатывания автовозврата по простою
или до двухчасовой фоновой уборки, если планшет унесли.



Все методы под `/api/ext/*`, ключ в заголовке `X-Api-Key`. Ключи создаются на вкладке
«API-ключи» и показываются один раз при создании: на сервере хранится только их хэш.

| Метод | Что делает |
|-------|------------|
| `GET /api/ext/devices` | планшеты, статус, привязка к месту |
| `GET /api/ext/workstations` | рабочие места |
| `POST /api/ext/workstations` | создать рабочее место |
| `POST /api/ext/enrollments` | код активации, можно сразу с `workstationExternalId` |
| `PUT /api/ext/devices/{id}/workstation` | сменить привязку планшета к месту |
| `POST /api/ext/show-document` | показать документ клиенту |
| `POST /api/ext/return-slides` | вернуть планшет к рекламе |
| `POST /api/ext/scan-request` | попросить отсканировать код и дождаться результата |
| `POST /api/ext/scan-cancel` | отменить сканирование |
| `GET /api/ext/scans` | последние считанные коды |

**Один вызов задаёт всё сразу:** теги, чекбоксы и группы.

```bash
curl -X POST -H "X-Api-Key: ВАШ_КЛЮЧ" -H "Content-Type: application/json" -d '{
  "workstationExternalId": "WS-204",
  "fields": {
    "ФИО": "Иванова Анна Петровна",
    "ДР": "01.01.1990",
    "Пол": "F",
    "email": "anna@example.by",
    "telephone": "+375291234567",
    "document": "MP1234567",
    "date": "20.08.2026",
    "Адрес регистрации": "г. Минск, ул. Ленина 1",
    "cross-border": true,
    "urine": true,
    "UG": false,
    "text1": "дополнительный текст"
  },
  "checkboxes": [
    {"key": "consent", "checked": true},
    {"label": "Согласен на рассылку", "checked": false, "required": false}
  ],
  "groups": [
    {"key": "transfer", "selected": "deny"}
  ]
}' https://signalr.zrobim.it/api/ext/show-document
```

**Адресация планшета:** либо `deviceId`, либо `workstationExternalId`. Если на одном
рабочем месте несколько планшетов, ответ будет 409 с просьбой указать `deviceId`: это
прямое следствие первого главного правила, документ не может уйти на два экрана.

**Ограничение частоты** по IP: внешнее API 600 запросов в минуту, сканирование 60,
подпись 60, диагностика 30, активация 20, вход в админку 10. Сделано, чтобы поток
запросов не мог занять ту же блокировку хранилища, которая нужна подписанию.

Полная документация со всеми примерами есть прямо в админке, вкладка **API**.

## Админка

Вход по паролю. Вкладки:

**Слайды** · **Документ** · **Подписи** · **Сканировать ШК/QR** · **Планшеты** ·
**Группы** · **Места** · **API-ключи** · **API** · **Логи** · **Уведомления**

Адресат рекламы и адресат документа выбираются **независимо** и на разных вкладках:
реклама может идти всем, документ только одному планшету.

Статусы планшетов, новые подписи, считанные коды и уведомления приходят в админку
живьём через SignalR, без перезагрузки страницы.

---

## Безопасность

**Две роли, одна схема авторизации.** Админ приходит с cookie `sk_admin`, планшет с
токеном `deviceId.секрет`. Токен планшета принимается в заголовке `Authorization:
Bearer`, а в параметре запроса `access_token` только на адресе хаба, потому что
браузерный WebSocket не умеет ставить заголовки.

**Секреты хранятся только как SHA-256.** Это касается и секретов планшетов, и ключей
внешнего API. Ключ FreeKiosk хранится на сервере и обратно в браузер не возвращается.

**Заголовки ответа** запрещают угадывание типа содержимого, встраивание в рамку и
передачу реферера. Политика безопасности содержимого разрешает только собственные
ресурсы, поэтому все библиотеки лежат локально, ни одного стороннего адреса.

**Пароль админки обязателен.** Сервис не стартует с пустым паролем или со значением
`admin`, и говорит об этом в журнале прямым текстом.

**За обратным прокси** пропишите его адрес в `KnownProxies`, иначе заголовок
`X-Forwarded-For` принимается от любого, кто дошёл до порта приложения.

## Двести планшетов одновременно

Система рассчитана на парк в две сотни планшетов и проверена на нём под нагрузкой. Замеры сняты
на одной машине: двести настоящих соединений, каждое со своего адреса, как и в сети филиала.

| Что мерилось | Сколько |
|---|---|
| подключение двухсот планшетов | 1,1 с |
| память: пусто и двести подключений | 94 и 140 МБ, около 230 КБ на планшет |
| запрос списка планшетов при двухстах подключённых | 9 мс |
| рассылка рекламы на двести планшетов | первому 10 мс, последнему 22 мс, дошло до всех |
| показ документа при двухстах подключённых | получатель ровно один |
| массовый разрыв и подъём всех заново | 0,6 с |
| три круга «подняли двести, уронили двести» | 145, 150, 152 МБ |

Рост памяти по кругам затухает: это оседание сборщика мусора, а не утечка. При утечке каждый
круг добавлял бы свои три десятка мегабайт.

**Что для этого сделано.** Состояние планшетов читается с диска один раз на весь список, а не по
разу на каждый планшет. Файлы держатся в памяти с проверкой метки времени: правку файла руками
рядом с работающей службой это не теряет. Уведомление «список планшетов изменился» собирается в
пачку: двести планшетов, поднявшихся разом, дают четыре уведомления вместо двухсот, а значит
четыре запроса списка от каждой открытой админки вместо двухсот. Задержки переподключения у
каждого планшета свои: с одинаковыми они возвращались бы одной секундой и били бы по службе
залпом ровно тогда, когда она только встала.

**Активация парка.** Ограничитель пропускает двадцать активаций в минуту с одного адреса. Планшеты
приходят каждый со своего, поэтому в сети филиала это не мешает. Но если планшеты выходят через
общий адрес, активация двухсот штук растянется на десять минут, и это не поломка, а защита от
перебора кодов.

## Хранилище

Обычные файлы и JSON, без внешней базы. Каталог задаётся `DataDir`, по умолчанию
`/var/lib/signaturekiosk`.

```
devices.json        планшеты (id, имя, хэш секрета, место, группы, адрес управления)
groups.json         группы планшетов
workstations.json   рабочие места (имя, внешний ID, описание)
enrollments.json    коды активации
apikeys.json        ключи внешнего API (только хэши)
states.json         что показывает каждый планшет прямо сейчас
document.json       шаблон документа
images.json         список картинок рекламы
images/             сами картинки
scans.json          считанные коды
alerts.json         уведомления оператору
kioskcontrol.json   настройки управления планшетами
schedule.json       правила расписания
keys/               ключи защиты данных ASP.NET
events.log          журнал сбоев (с ротацией)
signatures/<id>/    meta.json, signature.png, document.json
pdf/<id>.pdf        готовые PDF по каждой подписи
```

Все записи ограничены по размеру и количеству: списки подрезаются, длинные строки
обрезаются. Это не косметика, а защита: файл состояния переписывается под той же
блокировкой, которая нужна подписанию.

**Повреждённый файл не затирается.** Если файл окажется испорчен, он откладывается рядом
под именем с меткой времени (`devices.json.corrupt-20260820-193000`), в лог попадает запись
уровня «ошибка», а оператор получает уведомление. Записи из отложенного файла можно
разобрать руками. Молча подменить данные пустыми и не сказать об этом было бы хуже всего.

Запись в файл всегда идёт через временный файл с последующей заменой, поэтому обрыв
питания посреди записи не оставляет наполовину записанный файл.

## Локальный запуск и структура репозитория

Нужен .NET 10 SDK.

```bash
bash deploy/fetch-libs.sh          # один раз: подтянуть библиотеки в wwwroot/lib
cd src/SignatureKiosk
AdminPassword=test123 DataDir=./_data ASPNETCORE_URLS=http://127.0.0.1:5080 dotnet run
```

- То, что открывает планшет: <http://127.0.0.1:5080/> (в первый раз экран активации)
- Админка: <http://127.0.0.1:5080/admin>

```
src/SignatureKiosk/
  Program.cs                    REST API, статика, авторизация, внешнее API
  Hubs/KioskHub.cs              SignalR-хаб
  Auth/SkAuthHandler.cs         одна схема авторизации на планшет и на админа
  Services/
    StorageService.cs           файлы и JSON, единая блокировка
    KioskCoordinator.cs         что показывает каждый планшет
    DocumentTemplating.cs       теги, условия, разбор документа
    FieldSchema.cs              какие теги существуют и что принимают
    PdfService.cs               сборка PDF
    DeviceTracker.cs            кто сейчас на связи
    TokenAuthService.cs         коды активации и токены
    FreeKioskClient.cs          обращение к планшету по локальной сети
    KioskHealthCache.cs         последние показатели планшетов
    AlertService.cs             уведомления оператору
    AlertMonitor.cs             фоновый обход: связь, ошибки, здоровье, автолечение
    EventLogService.cs          журнал сбоев
    ScanBroker.cs               ожидание результата сканирования
  Models/Models.cs              модели и DTO
  Resources/*.ttf               встроенный шрифт для PDF
  wwwroot/                      index.html + kiosk.* (планшет), admin/ (админка), lib/
deploy/                         deploy.sh, fetch-libs.sh, systemd, nginx, инструкция
```

**Обновление версии** на сервере:

```bash
git pull
sudo bash deploy/deploy.sh
```

Данные и пароль при этом сохраняются. После обновления обязательно перезагрузите
страницу и на планшетах: WebView держит открытую страницу неделями, а старая версия
молча игнорирует всё новое.
